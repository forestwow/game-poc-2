# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

The Understudies is a prototype of a short roguelite for PC: a stage magician defends a box office, and every act played leaves behind an understudy that replays the route the player ran. `docs/vision.md` is the design; `docs/plan-prototype.md` is the plan, the decisions that settle the vision's open points, and the ticket list. Read the plan before changing a rule: where the two disagree, the plan is the later decision.

## Commands

All commands run from the repository root. `global.json` names the .NET SDK (10.0.1xx); warnings are errors.

```bash
dotnet build Understudies.sln --configuration Release                     # CI runs this first: `dotnet test` alone never compiles the game
dotnet test Understudies.sln --configuration Release                      # then this
dotnet test tests/Understudies.Core.Tests --filter "FullyQualifiedName~RngTests"   # one class or test
dotnet test tests/Understudies.Core.Tests --configuration Release --filter "FullyQualifiedName~ScriptedPlayersTests.PrintTheGuardsTable" --logger "console;verbosity=detailed"   # the scripted players' table: `[Explicit]`, so it runs only when named itself, and prints only with that logger
dotnet run --project src/Understudies.Game                                # play; Esc quits
dotnet run --project src/Understudies.Game -- --capture /tmp/frame.png --ticks 39570  # no play: the doors player of the guard plays for that many ticks (every act's curtain of sixty counted, a card taking none), the frame is saved and the game exits. The console says the tick each encore, program and the ovation is reached on; on the committed numbers act n begins on tick 4560 × (n − 1), and the show is played to its ovation on tick 45600
```

## Architecture

Three projects, with one-way dependencies: **Core** ← **Game** and **Core.Tests**. (The game also compiles one source file of the tests, `ScriptedPlayers.cs`, for the capture.)

- `src/Understudies.Core` is the game's rules, with no reference to MonoGame. `Simulation` owns the state and advances it one tick at a time from the magician's input of that tick; everything else reads the state and the events of the last tick (`Simulation.Events`, whose kinds `TickEventKind` lists; the next `Step` starts the list afresh, so whoever is driven by it reads it after every tick). A `TickEvent` is a kind and a place, and it says who: `Thrower` for a `Throw`, a `Hit` and a `Kill` (`TickEvent.TheMagician`, or an understudy by its place in `Simulation.Understudies`), and `CriticId` for a `Hit`, a `Kill` and an `ApplauseDropped` (`TickEvent.NoCritic` for the rest). An event is not state and none is in the hash, nor is which understudy threw a `ThrownCard` (`ThrownCard.Thrower`) while no rule reads it. The accumulator clock that turns frame time into whole ticks lives here too, where it can be tested. The same seed and inputs are meant to give the same result on every machine (a pinned state hash checks it across two, plan T19), so:
  - positions are `System.Numerics.Vector2` in world units, and the only arithmetic is + − × ÷ and the square root: no trigonometry;
  - (0, 0) is the stage's top-left corner and y grows downward. The top of the stage is the back wall: the floor starts at `stageFloorTop`, the magician's whole circle is kept on the floor, and `Tuning.Parse` refuses a stage door above it. Critics are kept on the floor by no rule. A test whose scene stands in the stage's top edge gives its own tuning a floor that starts at 0;
  - randomness comes only from `Randomness/Rng` (SplitMix64), never `System.Random`: the simulation draws from the seed its creator gives it (the game takes a played show's seed from the clock, and a capture's is fixed), each purpose from a stream of its own (`Rng.ForStream`, `RngStream`). A new purpose gets a new number, and no number is ever changed or given to another;
  - who enters when is planned once, when a `Simulation` is made: `Waves.Plan` buys each act's critics from `enemyKinds` with the act's budget and gives each a tick of the act and one of the doors open in it (`Simulation.Plan`, `ActEntries`, `ActEntriesMade`, `DoorIsOpen`). The budget is `firstActBudget`, `budgetGrowthPerAct` more in the second act, and that step bigger by `budgetGrowthRise` in every act after it (plan decision 27). The entries are spread evenly over the act, and then a share of them (`waveBurstShare`, picked evenly down the list) is moved to the last moment of a crowd before its own tick, a crowd every `waveBurstTime` seconds from the act's first tick: nothing more is drawn for a crowd, and with no share or no time the plan is the plan without crowds. A reload of the tuning does not plan it again. A critic's own numbers are its kind's (`EnemyKind`), which a `Critic` and a `PlannedEntry` name by its place in the list: the critic is the first kind and the stagehand the second (from act two, never turns on the magician), and the view and `Shows` know the two by those places. Every enemy on the stage is a `Critic`, whatever its kind. A test of another rule says exactly who enters through the constructor that takes a plan, with the helpers of `tests/Understudies.Core.Tests/Shows.cs`;
  - the simulation never iterates a `Dictionary` or a `HashSet` and never reads a clock;
  - a performance is `actsInPerformance` acts of `actLength` seconds. `Simulation.Phase` says where it stands: an act is played, it stands for an encore, its program is up, it is between two acts, it has ended in the ovation, or the show has closed (only the box office's fall closes it). `Step` changes the state only in an act, whose timer (`ActTicksLeft`) is counted last in the tick, and in an encore and a program, where it counts the offer's time and nothing else; in the other three it empties the events and nothing else. Between two acts the world stands until `GoOn`, which begins the next act with the magician whole and on its mark, makes the act just over an understudy and leaves everything else as it was. A test whose scene must outlast the committed act gives its own tuning a longer one;
  - the magician's fall does not end the act. From the blow that fells it (`MagicianHasFallen`, one `MagicianFell` event) to the next `GoOn` it takes no input, does not throw, and no critic turns on it; the recording of the act stops there, so that act's understudy leaves the stage (`Understudy.IsOnStage`) after the tick of the fall in every later act. The tick of the act is a count of its own (`_actTicksPlayed`), never the length of the recording;
  - an act is recorded as places, not inputs (plan decision 6): the magician's position after each tick (`Understudy.Route`), the tick and place of each Vanish, the self cards the act began with, and the tick and card of each encore taken in it (plan T24), and nothing else (no facing). An encore's tick is the act's count (`_actTicksPlayed`) while the encore is read, which is the number of the first tick the magician plays with the card. An `Understudy` (`Simulation.Understudies`, in the order of their acts) stands on `Route[tick]` and has the cards the magician played that tick with (`Understudy.Cards`: those its act began with and those of the encores recorded by that tick, worked out afresh in `Place` on every tick, so it throws on the tick of an encore as the magician did, and under an act's curtain it has only the first); before an act's first tick it stands on `Route[0]` with its throw ready, and when its route is shorter than the act it is off the stage (`IsOnStage`) for the rest of it. In a tick the understudies take their places right after the magician moves, each leaving a cloud on a recorded Vanish's tick (no `Vanish` event: that is the magician's own); then the cards fly, the critics walk, the magician throws and then each understudy in the order of their acts, all through the one `ThrowACard`, and a critic enters. A card is thrown ahead of its target, at where the two meet if the target repeats its last step (`Position - PreviousPosition`, made earlier in the same tick, so nothing of an older tick is read), and flies straight; the `ponytail:` comment there says what that misses. `ThrownCard.ThrownByMagician` says who threw a card. No rule for critics, clouds or cards looks at an understudy;
  - applause is the rule against standing by the box office (vision §4, plan decisions 26 and 27). A critic that falls to a card with `ThrownCard.ThrownByMagician` leaves one `Applause` where it fell (`Simulation.ApplauseOnTheFloor`, `ApplauseDropped` after the `Kill`); an understudy's card leaves none, whoever hurt the critic before, and no card does where the critic falls nearer than `applauseBoxOfficeRadius` to the box office's middle: the critic's place, never the magician's, and a fall exactly on the radius leaves its piece. A test of another rule whose scene falls by the box office gives its tuning a radius of nothing. A piece fades at the start of a tick, as a cloud thins, and lies for `applauseTime`. Only a magician that stands picks one up, right after it moves, within its radius and `applausePickUpReach` (`ApplausePickedUp`): no rule lets an understudy. `ActApplause` counts the act's pieces, and `EncoreApplause` those of them that no encore has been paid with yet. `GoOn` clears the floor and both counts: applause is never banked;
  - the cards (plan decisions 20 and 26). **The encore** is where the magician gets its self cards. It costs `EncoreCost` pieces: `encoreFirstCost`, and `encoreCostGrowth` more for every one of `EncoresTaken`, which counts through the performance. When a tick of an act is over, the act has time left, the magician has not fallen and `EncoreApplause` has reached the cost, the phase is `Phase.Encore`: `Simulation.Offer` has three different self cards, the leftmost first, drawn from the stream `RngStream.Encore`, and `Step` counts `OfferTicksLeft` down from `encoreTime` and does nothing else (the act's timer stands, no input is taken or kept). `Pick(place)` gives the magician the card at once, takes the cost from `EncoreApplause` (what is over stays, and opens the next encore when the next tick of the act is over), counts one more encore, and the act goes on; the tick that ends the encore's time is `Pick(0)`. A piece picked up on an act's last tick opens nothing. **The program** is where the chorus card comes from, and it is paid for by an encore: on the last tick of an act in which at least one encore was taken (`ActEncores`, which `GoOn` clears: an earlier act's encore does not count), and which has another after it and has not closed the show, the offer is the chorus card alone, the phase is `Phase.Program`, and `Step` counts `OfferTicksLeft` down from `programTime`. An act with no encore has no program and is between two acts at once: a player that picks up no applause gets nothing for its chorus either. `Pick(0)` or the end of that time takes it, which leaves the stage between two acts; a pick while nothing is offered or for a place the offer does not have does nothing, and `GoOn` does nothing in an encore or a program. The state is counts and never numbers: `SelfCards` is how many of each of the five self cards somebody has, `MagicianCards` the magician's, `Understudy.Cards` those that understudy has on this tick of the act (what its act began with, kept apart in `_recordingCards` while the act is played, and each card of that act's encores from its tick on, kept in `_encores`; the Vanish cooldown card changes nothing for an understudy, whose Vanishes are recorded ticks), and `ChorusCards` how many chorus cards were taken. The numbers are worked out from the tuning of now where they are used: in the one `ThrowACard` (range, damage, the time to the next throw and how many cards, each at a critic of its own, the nearest first, and none for a critic that is not there; the chorus damage for an understudy only) and in `VanishCooldownTicks`. A `ThrownCard` carries the damage it was thrown with. The smaller rule was taken for one more card: no spread when there is one target. A test of another rule whose act picks up as much applause as an encore costs meets an encore, and then a program: it gives its tuning an `EncoreFirstCost` nobody can pay, or an `ApplauseTime` of nothing, or calls `Pick(0)` before every tick and before `GoOn`. A test that needs a certain card looks for a seed whose encores offer it (`CardTests.SeedWhoseEncores`): what an encore offers follows from the seed and from how many encores were opened before it alone. The stream `RngStream.Program` is drawn from no more;
  - `Simulation.ComputeStateHash` is an FNV-1a hash of everything that decides what happens next. State added to the simulation is added to it in the same change, a `float` by its bits; what only the view reads (the positions before the last tick, the events, where a card was thrown from) stays out. It walks every recording whole, so it is for tests and scripted players and not for every frame;
  - a time in `tuning.json` is in seconds and a rule counts it in whole ticks;
  - `tuning.json` at the repository root is the only place a rule's number lives (the tick rate is the one constant in code; the juice's numbers decide no rule and are constants in the view). `Tuning` is the record parsed from it, and `Simulation` is given one by whoever creates it. A new number is a new member of `Tuning` and a new key in the file: an unknown key and a missing key are both refused, at any depth.
- `src/Understudies.Game` is the MonoGame (DesktopGL) layer: input, drawing, sound. It holds no rules: it feeds the simulation the player's input each tick and draws what the simulation reports, with positions interpolated between the last two ticks. There is no content pipeline. The figures (the magician, the critic, the stagehand, the box office) are pixel-art sprites read at start-up with `Texture2D.FromFile` from `art/ludo/sprites/` (`ReadSheet`; found as `tuning.json` is, and copied beside the built game), and so is the set (plan T07d): the floor's boards and the back wall's curtain, two pictures laid side by side by `Lay` in a batch that lets a picture go round, the three stage doors (a shut picture and a lit one, by `DoorIsOpen`) and the footlights along the front edge, which are drawn by `DrawFigure` as a figure is: the doors under the figures, so that a door hides nobody, and the footlights over them, out while a program is read. Everything else is shapes. A walking figure is a sheet of three rows of three frames for each of three views (toward the viewer, away, and to the right, mirrored for the left); `DrawFigure` picks the view from where the figure goes and the frame from the view's own clock, and draws a sprite pixel as a whole number of screen pixels, unsmoothed, so a figure's size on the screen follows the window in steps (the window opens at 1024 × 576, where a sprite pixel is one screen pixel). The flash is a white copy of the sprite drawn over it, an understudy is the magician's sprite washed with its act's colour, and a standing figure has a shadow. `art/prompt-guide.md` is the recipe a new figure is made by. What makes a blow felt (flashes, scraps, fading bodies, the shake, the hit-stop, and the cards' effects of plan T22: a flick at a throwing hand, a burst where a card strikes and one where its critic falls, the two bursts sheets played through once; and a puff of scraps at an understudy that gains a card of its act's encores, which no event reports: `Feed` sees that it has more cards than a tick before; the critic that flashes is the one a `Hit` names, kept by its id until its `Kill`; and an understudy's throw is a smaller, dimmer flick in its card's face, `Effect.UnderstudyFlick`, so that the past is told from the present) is the view's own state, in `Juice.cs`: `UnderstudiesGame.Tick` feeds it the simulation after every tick (whatever else the events drive, the sound for one, is fed there too), the frame's time advances it, and the drawing asks it what to add. The capture mode feeds and advances it the same way, a sixtieth of a second a tick. It is advanced in every phase: between two acts the simulation stands and the juice still settles. Its numbers are named constants at the top of that file. A figure is drawn by `DrawFigure` alone, which is asked for a flash, a fallen pose and an opacity: nothing paints over a figure with a shape of its own, so the juice holds whatever a figure is drawn from. Text is `FontStashSharp.MonoGame` over a system font found at start-up (the first of `FontFiles` that exists; with none the game runs without text and says so on the console), and it is drawn in screen pixels at a size taken from the window, never scaled up from world units. An understudy is the magician's figure through `DrawFigure`'s `tint` and `opacity`, never a figure of its own. The floor within `applauseBoxOfficeRadius` of the box office is a shade darker with a thin broken line round it (`DrawTheQuietFloor`, first in the batch of what lies flat, kept to the floor; its numbers are constants beside the colours): it is how the player reads where a fall earns no applause. The program's screen is `ProgramScreen.cs`, a second part of the one `UnderstudiesGame` class: the panels, the choosing and the card just taken, for an encore's three cards as for the program's one (`IsOffered` is either). `Update` reads a frame's presses by the phase the frame began in, so one press never does two things: while cards are offered `ChooseInTheProgram` moves the highlight and takes a card (`Take`), and otherwise Space or A is the Vanish and Enter or Start is `GoOn`. Every press there is an edge against `_keysBefore` and `_padBefore`, the stick too, and that is all that keeps a key held since the act from taking a card: an input added to the program must be an edge as well. An encore opens in the middle of a fight, so for its first `EncoreGuardTime` nothing is taken, held or pressed. The view keeps a copy of the offer (`_offered`, made in `Tick` when an encore or a program opens), because `Pick` empties the simulation's: the program's card taken is shown from the copy for `TakenTime`, in which `GoOn` is not called, an encore's is gone at once with the same chime, and an offer that ended inside `Tick` is the clock's pick of the leftmost. The bar on the back wall is the way to the next encore, `EncoreApplause` over `EncoreCost`, with the two numbers beside it. `Describe` names a card and what it changes, from the tuning. `Write` draws words in screen pixels from a point of the stage (`_scale` and `_corner` are the frame's). The capture is played by the doors player of the guard: `ScriptedPlayers.cs`, the tests' own file, is compiled into the game as well (a `Compile` link in the project file, so there is one copy), and `Capture` asks it for every tick's input and for which card to take. A card is taken and the next act gone on to before the tick, so neither takes any of a capture's ticks, and a capture that ends on the tick an encore or a program opens shows that screen; the console is told those ticks. Whatever changes that player or what it meets moves the frames: take `art/frames` again in the same change. Inside this project `Game` means the namespace, so MonoGame's base class is written `Microsoft.Xna.Framework.Game`.
  - the sound is `Sound.cs`, the view's own state like the juice and fed in `Tick` beside it: seven short sounds worked out in code at start-up and handed to MonoGame as `SoundEffect`s (no sound file, no content pipeline), one for each of the event kinds `Throw`, `Hit`, `Kill`, `Vanish`, `BoxOfficeStruck`, `MagicianHurt` and `ApplausePickedUp`. A kind of event that has no sound there is silent. What an understudy did (an event whose `Thrower` is not the magician: its throw, its hit, its kill) plays the same sound quieter and lower (`UnderstudyLevel`, `UnderstudyPitch`), and the magician's own sound is not held back by the gap after an understudy's. How loud each is, the gap between two starts of one sound and every recipe are named constants at the top of that file. A capture makes no `SoundEffect`, so it opens no audio device, and a machine that has none runs the game silent. A sound cannot be reviewed by a captured frame: a changed one is measured by hand (its length, its peak, that it starts and ends at zero: nothing in the repository does it) and then judged by the owner's ear.
- `tests/Understudies.Core.Tests` is NUnit: the rule tests and the scripted players that measure the balance (plan T19, decision 22). `ScriptedPlayers` has the two players, the orbit player and the doors player, each a function from the simulation's public surface to one tick's input, with no state and no randomness of its own and Core's arithmetic rule; the one order both pick an encore's card by; and `Play`, which plays a performance to its end, taking every encore's card by that order and a program's card at once, and returns its record act by act. The orbit player is played on three circles (`OrbitRadii`: on the box office, close round it, out where the throw still reaches across), and the design has beaten hiding on a seed only when all three lost: a tuning that beats one circle has beaten a script. The doors player holds the newest door, steps back from a critic that is upon it, and goes back to the box office while a critic is at it. The committed tuning is tuned to the guard (plan T20), and `ScriptedPlayersTests.TheGuard_OnTheCommittedTuning_...` is the ordinary test that holds it there: over the seeds 1 to 20 the orbit loses the box office by the end of act six in at least 16 and the doors player finishes act ten in at least 16. A change to `tuning.json`, to a rule or to a player that breaks it is a finding about the design, not a number to loosen. `PrintTheGuardsTable` plays the same performances and prints how each ended, act by act with each act's applause and encores, and the guard's two counts; `PrintTheVariants` (`[Explicit]` too) is the instrument of plan T26: for every variant of the committed tuning in the file the environment variable `UNDERSTUDIES_VARIANTS` names (a line each, `name | { "key": value }`), on the seeds 1 to 20 and 101 to 120, the guard's counts, how and in which act each player lost (the magician up or down), and by act the encores, the applause, the box office and the most critics at once; beside the guard's players it plays the doors player with no applause in act one and the orbit on circles of 9 and 13, which count for nothing in the guard. The second set of seeds is in that instrument only. The two `..._EndsInThePinnedStateHashOnEveryMachine` tests are the pinned state hash of decision 9: two scripted performances (the doors player on the committed tuning; the orbit player on a circle of nine with a fuller first act and no rise, with Vanishes, stuns and blows on the box office: on the guard's own circles no fall leaves applause and the orbit does not live three acts) whose hashes, at the end of act three and at the end, must be the same on macOS ARM and in CI on Linux x64. A change to `tuning.json`, to a rule or to a player changes them: pin the numbers again from the failure's message and say so in the pull request. It changes what a capture shows too: take `art/frames` again. If the two machines ever disagree, do not make it pass: keep a pin for each machine and tell the owner. Every act opens with a curtain in which `Step` only counts the curtain down, so a test scene that counts its ticks from the first tick of an act sets `CurtainTime = 0f` in its own tuning (no curtain); `CurtainTests` are the ones with a curtain.
- `tuning.json` is copied by the project files beside the tests and beside the built game. The tests read that copy through `CommittedTuning`, so a test never carries its own numbers. The game reads `tuning.json` in the current directory first (the committed file itself, as commands run from the root) and the copy beside the executable otherwise; F5 reads it again while the game runs.

## How the work runs

- One ticket of `docs/plan-prototype.md` is one branch (`tNN-short-name`) and one small pull request into `main`, whose title starts with the ticket id (`T04: ...`). Tickets are taken in order.
- Work in a git worktree; the owner's checkout stays on `main`.
- Write the test first for every rule in Core. The view and the juice have no tests: they are judged by eye at the plan's stops, and by a captured frame in review.
- Before a merge, a separate agent with a clean context reviews the pull request with the `mattpocock-skills:code-review` skill (fixed point `main`; the spec is the ticket in the plan) and the `ponytail:ponytail-review` skill. Fix or answer what it finds, wait for green CI, then merge.
- The plan's stops are where the owner plays and judges. The loop does not wait at a stop: it announces it and goes on.
- Build the smallest thing the ticket asks for: no abstraction, option or layer for a later ticket. Mark a deliberate shortcut that has a known ceiling with a `ponytail:` comment naming the ceiling.
- Everything in the repository is in English. There is no study journal in this project.
